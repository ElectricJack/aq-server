# Implement the native AQ Performance page

**Proposed implementation · 24 November 2026 · aq-server and aq-dashboard**

Build the [fleet performance design](../specs/2026-11-24-fleet-performance-and-model-efficiency-design.md) as one read-only dashboard feature plus an owner-managed reporting preference. Ship a useful first release with the existing AQ server, PostgreSQL and dashboard. Existing worker protocols and playbooks can run as-is. The rollout target is a reproducible baseline on the two worker machines. Numerical performance goals follow that baseline.

## First-release contract

| Surface | Deliverable |
|---|---|
| Delivery and quality, last seven days | Show distinct confirmed completions, verified target-branch merges and first-pass acceptance with their denominators. Where configured, show policy-defined deliveries and median/p90 first-ready-to-delivery. The completion and merge clocks are visible independently. |
| Holds, now | Show held count, oldest age and missed scheduled checks. List task, hold reason, responsible party and next check when known, linking to existing Work detail. |
| Machine utilization, last 24 hours | One aligned occupancy row per machine, including zero activity. Show enabled online capacity, occupied/free slots and stale, offline and paused intervals. Overlay one fleet ready count. Highlight at least ten consecutive observed minutes idle with queued work. |
| Queueing diagnostics | Count observed admission or offer decisions by bounded reason. Let a fleet operator inspect a few task-linked examples, coverage and measured eligible-to-claim delays. Report only the intervals the server actually witnessed. |
| Model efficiency, last seven days | Report token categories, cost, currency, basis, missing prices and coverage by actual model. On a task, retain the first routing decision alongside retries, subagent use and escalations. Show whether a first submission was accepted. This supplies evidence for a later cost-per-success comparison. |

Defer exact historical matching of tasks to all free slots, continuous CPU collection, automated goal evaluation, defect-adjusted comparisons, external delivery receipt adapters and the optional Prometheus/Perses integration. The native page and its acceptance suite must work with monitoring services absent.

## Contracts to freeze before parallel coding

The integration lead owns a short contract commit and publishes its SHA to every lane. This is the only shared prerequisite. Pin each repository’s base SHA and record the component versions in the handoff. Inspect the current schemas and data owners before adding a table. In particular, distinguish a Graph ready transition from the first time a bounded ready page happens to contain a task. Document source, identity, authoritative time, visibility scope and missing-data behavior for each metric in the contract commit. An absent source permits a partial metric.

**Server and dashboard boundary.** Use the dashboard API prefix, existing response envelope and capability negotiation. Register optional capability `performance.metrics.v1`. Proposed read routes under `/api/v1/performance` are `summary`, `machines`, `holds` and `tasks/{task_id}`. Summary and hold reads accept the authorized project scope. Machine timelines and scheduler examples require fleet access. Task detail reuses task visibility checks. The first response provides a server-generated UTC cutoff that subsequent paged reads reuse. Presets are seven days for outcomes and 24 hours for machines, with a maximum seven-day history query. Current holds carry their own observation time. Pages use a stable tie-break and a bounded cursor.

Common response fields carry definition version, window, cutoff, observation freshness and coverage. A ratio includes numerator and denominator; zero denominator yields a null value. Return an unavailable section with a reason when an independent source is missing. The fixtures must distinguish measured zero, partial/lower bound, unknown and delivery not tracked. Example: 12 confirmed completions, five merges, two completions with a known ready timestamp, delivery tracking off. Display 12, five and timing coverage 2/12; the configured delivery figure is blank and labelled. No task identifiers, reasons or aggregated project totals from another authorized scope may leak into these counts.

**Configuration.** Use the existing owner settings command and optimistic revision pattern to set a project default or work-class override. Support `not_tracked`, `confirmed_completion` and `target_branch_merge`. A merge definition references the project repository and target ref. Prefer the more specific work-class setting, then the project default, then not tracked. Store immutable effective revisions. Bind first-ready cohorts to the version effective at their first authoritative ready time. Earlier tasks without a known applicable definition retain untracked/unknown coverage. A read cannot change task or playbook state. Implement explicit setting, readback and restore-to-default through the existing owner command surface; the first dashboard can display a read-only explanation of the selected definition.

**Fixtures and shared files.** The lead owns route registration, feature advertisement, wire examples, module declarations, integration-test module registration, dependency manifests and migration numbering. Freeze example JSON for populated, empty, partial, stale and forbidden scopes. Give each backend lane a typed input/output seam and fixture directory. Keep Rust and TypeScript examples identical by comparing canonical JSON in integration. Each lane owns its module, focused tests and any migration SQL fragment. The lead assembles the authoritative migration and updates format/compatibility metadata once. Refresh current migration head at integration; never reserve a number on the assumption that main will stand still.

## Sol agent worktrees and ownership

Use one Sol agent per implementation lane. The lead maintains two integration worktrees. Lane branches are local, independently testable and merged only into their corresponding integration branch during development. Begin lane work after the contract is frozen; UI and qualification can implement against the committed examples while producer work is underway.

| Lane | Repo and exclusive ownership | Handoff and focused proof |
|---|---|---|
| A · Outcomes | aq-server. New performance outcome reader and delivery definition settings handler. Reuse completion, review and merge receipts. Own definition persistence and effective-version SQL fragment. | Return summary and drill-down task IDs. | B · Holds and machines | aq-server. New performance hold reader, history sampler and pruning code. Start from swarm assembly and supervisor hold views. | C · Queue diagnostics | aq-server. Instrument existing scheduling decision sites in profiled execution and join to durable claim evidence. Own bounded diagnostic storage fragment and reader. | Show actual skip reasons, first eligible observation, claim time and observation loss. | D · Usage and routing | aq-server. New usage rollup and task-attribution reader, plus the first-route capture at the durable launch/selection boundary if existing provenance is insufficient. Own attribution SQL fragment. | Include a cheaper first attempt, delegated usage, escalation, a failed attempt, a corrected call and an unknown price. Verify that totals reconcile and a retry cannot overwrite the initial route. |
| E · Performance page | aq-dashboard. Own the feature, API adapter, fixtures/mocks, capability-gated route and navigation. A and C both need task clocks. The lead owns the shared clock and source-identity definitions. B and C both use machine identity; C only emits diagnostic evidence, B owns sampled occupancy. C owns changes to poll workflow; D owns durable provenance. If one edit site is unavoidable for two lanes, its owner accepts a small patch from the other lane. Keep the worker out of the critical path: a missing worker-only signal appears as unknown for this release. Do not change the wire protocol to fill a chart.

### Create the worktrees at implementation kickoff

Run from the workspace root after the spec branch and target main revisions are available locally. Execute the first block once. Then have the lead land the shared server contract on the server integration branch and the matching dashboard fixture on the dashboard integration branch before running the second block.

```bash
git -C aq-server fetch origin main
git -C aq-dashboard fetch origin main
git -C aq-server worktree add -b perf/integrate "$PWD/wt/perf-server" origin/main
git -C aq-dashboard worktree add -b perf/integrate "$PWD/wt/perf-dashboard" origin/main
# Carry both the reviewed design and this implementation plan into the server candidate.
git -C wt/perf-server merge --no-edit design/fleet-performance-metrics
```

```bash
server_contract=$(git -C wt/perf-server rev-parse HEAD)
dashboard_contract=$(git -C wt/perf-dashboard rev-parse HEAD)
for lane in outcomes capacity scheduling usage qualification; do
  git -C aq-server worktree add -b "perf/$lane" "$PWD/wt/perf-$lane" "$server_contract"

On resume inspect `git worktree list` and use the existing branch and path. Each agent reports its commit SHA, base contract SHA, tests run, coverage limits, and shared changes requested. Honor each repo’s build guidance and use separate Rust target directories. Stagger heavy links on the shared host while keeping development and lightweight tests parallel.

## Implementation notes for the lanes

**A · Outcomes.** Aggregate completion across confirmed settlement paths by task, and use task-linked forge evidence independently. A worker submission or successful playbook run can be pending delivery. A verified merge can precede, follow, or never produce AQ completion. Use first-ready across retries; omit unknown clocks from quantiles and count them in coverage. Compute median/p90 with a documented percentile convention (continuous percentile in PostgreSQL). Define first-pass acceptance from the first adjudicated submission and substantive correction evidence. Classify ambiguous decisions as unknown. Keep undetermined, cancelled, held and returned outcomes visible in drill-downs. A verified merge count and a task-delivery count have different units; label them and deduplicate each by its proper identity.

**B · Holds and machines.** The current [hold follow-up view](../../../crates/aq-server/migrations/0173_supervisor_hold_followups.sql) and [swarm contract](../../../crates/aq-dashboard-contract/src/swarm_contract.rs) are starting points. Sample the same inventory owners used by the dashboard; reuse historic observations only after proving freshness and completeness. Otherwise upsert one row per machine and one fleet row per UTC minute, with seven-day retention. Prevent partial ticks being mistaken for complete snapshots. Two machines at this cadence produce at most 30,240 sample rows per week. Persist no heartbeat payloads. Derive ready count only from a complete, scoped source; a truncated scheduler page is a lower bound. A gap, disabled machine or stale heartbeat breaks an idle stretch. Concurrent capacity is time-weighted. Ten idle minutes on two machines with one queued task is evidence of concurrent idleness, not twenty minutes of lost scheduling opportunity.

**C · Queueing.** Start at [the producer polling path](../../../crates/aq-server/src/profiled_execution/producer/workflow.rs). It already distinguishes blocked assessments, skipped routes, zero available slots, and contention during offer assembly. Borrow the reason where the owning code produces it; preserve “unknown” for empty responses without a known cause. First assessment can precede final route or admission checks. Start a measured eligible-to-claim clock only when AQ observes both compatible idle capacity and a task passing applicable gates. End on a verified claim for that task. Label the metric **first observed eligible to claim** and show the covered claim count alongside all claims. Earlier eligibility may be unobserved. Do not measure aborted episodes as successful claims; close them on lost eligibility, stale capacity or a source gap. With no suitable earlier observation, report missing timing. Deduplicate retries using existing operation identity and task/generation. Aggregate bounded reason counts by minute and keep a capped sample of examples. Use a bounded nonblocking handoff for observations, publish drop counts and exclude gaps. Never add a synchronous database or network write to a poll/claim transaction solely for metrics.

**D · Usage.** Start from the [canonical accounting projection](../../../crates/aq-accounting/src/projection.rs) and [usage schema](../../../crates/aq-observation-api/artifacts/usage.schema.json). Prefer rereading the bounded latest canonical contributions to incrementing totals when a receipt arrives. A late correction replaces the previous contribution. Honor pricing revision, category overlap, distinct currencies, time window and cost basis. Where only session totals exist, expose those with their known scope; do not assign lifetime totals to a weekly call window. Bind initial routing identity at its earliest durable decision; distinguish intended candidate, actual executing model and policy revision. Scope retries by task lineage, and retain delegated attribution only where evidenced. Show first-route unknown for historical gaps, shared overhead as its own category, and observed zero separately from missing data. Reuse the v1 Claude message deduplication, Codex response/cumulative-reset and cached-input overlap cases as accounting parity fixtures.

**E · UI.** Put outcomes and coverage above aligned worker rows and a single ready-queue trend. Follow with actionable holds and usage by model; link to the task evidence, including reasons for gaps. Show both machines even when one is idle. Keep existing dashboard destinations usable when the optional capability is absent. Offer distinct “not tracked”, “no events in window”, “data incomplete” and “temporarily unavailable” states. Format rates only when denominators are positive. Enforce permission on the server as well as hiding unauthorized links.

**F · Reference fixture.** Give a task a first-ready time of 09:00, first observed eligibility at 09:02, claim at 09:05, a failed cheaper attempt costing an estimated 0.10, a delegated call costing 0.05 and an escalated attempt costing 0.35 in the same currency and basis. Record a merge at 10:00 and confirmed completion at 10:20. Expected values are a three-minute observed queue delay, 60 minutes to merge, 80 minutes to completion, one delivered task under either configured milestone and total estimated cost 0.50. Replay receipts, then raise the delegated cost to 0.07 via correction and expect 0.52. Add another task held since 09:00 and reminded at 10:00; its age at 10:30 is 90 minutes. Add an idle incompatible machine, a missing heartbeat and another project invisible to the test actor. With tracking off, observed completion and merge counts survive and configured deliveries become untracked. Repeat replay after server restart.

## Integration, release and rollback

1. **Lead freezes interfaces and storage seams.** Record which existing sources can support first-ready, first-route, verified claim, readiness counts and quality evidence. Each unavailable fact receives an explicit coverage reason. Agents can prepare fixtures and identify source owners during this step.
2. **Merge in dependency order.** The lead assembles the lanes’ schema fragments, registers migrations and tests, then integrates A–D independently against the shared contract. Merge E into the dashboard integration branch after fixture tests. F’s cross-lane checks run after the server is assembled. A contract revision needs a new fixture in both repos and acknowledgment from affected lanes. Keep a single integration PR per changed repository, with cross-links and compatible revisions.
3. **Qualify locally.** Run affected Rust package tests and focused cases in the existing `it_dashboard`, `it_access`, `it_profiled` and `it_schema` binaries as applicable. Check fresh install, previous-format upgrade and repository build budgets. In the dashboard run `pnpm typecheck`, affected tests via `pnpm test`, and `pnpm build`. Exercise a mixed-version pair, project access, concurrency, restart, corrections, missing sources and read-only behavior with sampling disabled.
4. **Measure overhead.** Run the same representative polling workload with observation disabled and enabled. Record sample size, throughput, poll p50/p95, dropped observations, database write rate and query plans. Require bounded memory and storage, unchanged admission results, and no instrument-induced poll errors. Investigate latency movement outside repeated baseline variation. Load the maximum seven-day page and verify indexed reads and bounded responses.
5. **Roll out server before dashboard.** Use the project’s normal release procedure and schema compatibility checks. Expose the capability only when the server can serve the contract. F records one real interval for each machine, one long hold and one escalated task against source evidence; disclose any missing coverage. For a site with no escalations yet, the deterministic fixture proves arithmetic and the production panel remains labelled with observed coverage.
6. **Rollback independently.** Disable the sampler/diagnostic capture and remove or hide the optional page if collection affects scheduling. Historical samples can expire naturally. Retain authoritative work, cost and receipt records. Follow state-format compatibility for any server binary rollback. Confirm normal worker polling and task progress with the Performance page unavailable.

Implementation is complete when the native page, settings and scoped API pass the reference fixtures, performance checks and release verification. Production performance targets are a separate decision after a measured work cycle.
